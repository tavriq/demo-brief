# Проверка ТЗ

Черновик 08.10, автор правит по опыту аналитика. Две части: проверки кодом (бесплатно, всегда одинаково) и чек-лист модели-ревьюера. ТЗ красное, если есть хотя бы одна ошибка кода или ревьюер отметил хотя бы один пункт «нет». Красное ТЗ уходит автору с замечаниями, не больше 2 кругов. После второго круга конвейер идёт дальше с пометкой «ТЗ с замечаниями».

## Кодом (`app/checks.py`)

| id | Проверка | Уровень |
|---|---|---|
| K1 | все разделы заполнены: цель и метрика, роли, сценарии, данные, НФТ, критерии, риски, оценка (интеграции могут быть пустыми) | ошибка |
| K2 | id уникальны и по формату R1/S1/N1/A1 | ошибка |
| K3 | у сценария роль из списка ролей | ошибка |
| K4 | у каждой роли есть сценарий | ошибка |
| K5 | у каждого сценария есть критерий приёмки (`scenario` или `target` = его id) | ошибка |
| K6 | критерий `screen` ссылается на существующий сценарий, `field` — на существующее поле `Сущность.поле`, у `review` target пустой | ошибка |
| K7 | в критерии нет расплывчатых слов без числа: удобн, быстр, интуитивн, современ, качествен, красив, понятн, легк, оптимальн, эффективн, надёжн/надежн, простой | ошибка |
| K8 | в метрике НФТ и в метрике цели есть число | ошибка |
| K9 | сумма частей оценки равна `total_days`, у каждой части дней > 0 | ошибка |
| K10 | у риска есть что делаем, у интеграции — что при недоступности | ошибка |
| K11 | в сценарии хотя бы 2 шага и результат | ошибка |
| K12 | массив длиннее предела (`schema.LIMITS`) — обрезан | предупреждение |

## Чек-лист ревьюера (модель, `SPEC_REVIEW`)

| id | Пункт |
|---|---|
| Ч1 | Цель про бизнес, а не про систему, и метрика её действительно измеряет |
| Ч2 | Роли — реальные люди из брифа; нет лишних и нет пропущенных |
| Ч3 | Сценарии описывают действия человека и результат, а не устройство экранов |
| Ч4 | Данных хватает для сценариев: всё, что сценарий показывает или вводит, есть в разделе «Данные» |
| Ч5 | Нет противоречий между разделами: сценарии, данные, интеграции и НФТ не спорят друг с другом и с брифом |
| Ч6 | Критерии приёмки проверяются «да / нет» человеком, который не писал ТЗ |
| Ч7 | Допущения названы явно, вопросы клиенту — про то, что меняет объём или оценку |
| Ч8 | Оценка в днях правдоподобна для объёма сценариев и интеграций |

## Прототип (`app/checks.py`)

| id | Проверка |
|---|---|
| P1 | HTML разбирается парсером, есть `<body>` |
| P2 | размер не больше 80 000 байт |
| P3 | нет сети: внешних `src`/`href`/`action`/`srcset`/`url(…)`/`@import`, `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `sendBeacon`, `<iframe>`, `<object>`, `<embed>`, `<base>`, `<meta http-equiv="refresh">` |
| P4 | у каждого сценария есть экран: элемент с `data-screen="S1"` |
| P5 | переходы между экранами: хотя бы один `data-go="S…"` (предупреждение) |

P1–P4 не прошли или ответ обрезан — прототип уходит автору с замечаниями один раз. Прототип с P2 или P3 не сохраняется. P3 ловит явные адреса, но обойти его можно (адрес, собранный из частей), поэтому сеть закрывают ещё CSP прототипа и `frame-src 'self'` на странице.
